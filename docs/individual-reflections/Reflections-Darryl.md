# Reflection on Basic Agentic Software Engineering

Working on ClubStock changed how I think about Agentic Software Engineering. At the start, I mostly saw skills as a way to abstract long prompts implementation, testing, review, and commits like how functions in programming abstract programming logic. After using them more, I realised their bigger value was in making assumptions and missing work easier to notice. The agent could produce code and plans very quickly, but that did not mean the implementation was complete or that it had understood the requirements correctly. Over time, I started treating the agent less like an autonomous developer and more like a collaborator whose work still needed checkpoints and evidence.

## `implement`: Approval Gateway and Requirements Review

The most useful part of the workflow was the approval step before implementation. Before starting a milestone, the agent had to prepare a brief covering the scope, design decisions, test cases, files that would be affected, and possible integration issues. I had to approve this before it could start changing source code. This mattered in ClubStock because many of the requirements are connected. For example, a Member making a request affects the Exco queue, approving a request affects stock availability, and verifying a return affects both the loan and equipment states. Having to review the plan first forced me to think about these dependencies before any code was written. It also made it harder for the agent to quietly expand the task or make assumptions that I had not agreed with. I found this quite similar to doing a lightweight requirements review in a real team where it takes more time at the start, but it can save a lot of tedious rework later.

## `implement`: Enforceable Workflow State Transitions

At the same time, I found that having a workflow is not enough if the agent does not follow it properly. During the Exco return and loss verification task, the agent stopped after only part of the implementation was done, even though the workflow still required UI work, focused tests, quality review, verification, and manual testing. I was puzzled as to why it kept stopping progress and made codex do an audit of itself. Codex revealed that there was no issue with the skill prompt and it had no clear reason as to why it stopped. That made it clear that an agent can finish a small part of a task and still wrongly treat that as a reasonable stopping point. I tightened the workflow after this so that an iteration could not be handed off while it was still in an implementation state, and automated verification had to provide evidence for every planned test case. This made me realise that orchestration works better when the workflow has clear and enforceable state transitions, rather than just instructions that the agent is expected to remember.

## `clubstock-verify`: Finding Precision and Ordering Bugs

The verification skill also helped uncover some issues that I probably would not have noticed immediately. One example was SQLite’s julianday() representation, which rounded timestamps to milliseconds. This meant that loan requests submitted very close together could be ordered incorrectly, even though the requirement said that Exco should see them from earliest to latest submission time. The fix was to use a timestamp ordering approach that preserved more precision, together with a regression test where the request IDs were deliberately in a different order from the timestamps. What I took away from this was that agentic testing can be useful for turning a subtle issue into a repeatable test, but the developer still needs enough understanding of the underlying behaviour to question an implementation that looks reasonable on the surface.

## `clubstock-quality-review`: Looking Beyond Happy-Path Behaviour

The quality review step was also useful because it found problems that normal happy-path testing did not. In the Exco report verification screen, the UI could show that a resolution had succeeded even if the refresh afterwards failed, which meant the user might still be looking at stale data. Another issue was that Exco could only see an opaque key for a damage-report image instead of viewing the actual evidence. These findings led to safer feedback in the UI, stale actions being disabled when refreshes failed, and a managed and authorised way to display evidence images. This made me see quality review as something that checks more than whether a feature technically works. It also looks at whether the feature behaves clearly and safely when things go wrong.

## `commit`: Traceability Across a Feature

The commit skill also made me appreciate the importance of traceability in agentic development. Features such as Exco report verification touched services, DTOs, controllers, FXML screens, application wiring, and tests. Keeping these changes together in one focused commit made the feature much easier to review and explain. It also made it easier to check whether the implementation, tests, and related documentation had changed together. The agent could generate changes quickly, but disciplined commits were what made those changes easier to understand later.

## Key Takeaway: Human Accountability in Agentic SE

Overall, my main takeaway is that Agentic SE is not about handing responsibility over to an AI agent. The agent is useful because it can speed up analysis, implementation, testing, and review, but the human still needs to control the scope and decide whether the work is actually correct. For me, the most useful parts of the workflow were the approval gates, verification evidence, quality review, and manual testing, because they kept that responsibility with the developer rather than the agent.
